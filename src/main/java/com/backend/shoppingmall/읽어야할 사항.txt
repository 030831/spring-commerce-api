나는 Spring Boot, JPA, MySQL 기반의 미니 쇼핑몰 백엔드 API 프로젝트를 만들고 있다.

이 프로젝트는 포트폴리오의 메인 프로젝트라기보다는, 혼자서 Spring Boot, JPA, MySQL, DB 모델링, REST API 구현 흐름을 직접 경험해본 학습형 프로젝트다. 다만 GitHub에 올릴 예정이고, 나중에 포트폴리오 보조 자료로 사용할 수 있도록 코드와 문서를 깔끔하게 정리하고 싶다.

현재 목표는 처음부터 복잡한 쇼핑몰을 만드는 것이 아니라, 아주 작은 범위에서 시작하는 것이다.

현재 1차 요구사항은 다음과 같다.

1. 쇼핑몰 백엔드 API 서버를 구현한다.
2. 회원은 상품을 주문할 수 있다.
3. 회원은 자신의 주문 내역을 조회할 수 있다.
4. 하나의 주문에는 상품이 여러 개 들어갈 수 있다.

즉, 지금은 회원, 상품, 주문, 주문상품 구조와 JPA 연관관계를 이해하는 것이 핵심이다.

현재 도메인은 다음 4개로 시작한다.

- Member
- Product
- Order
- OrderItem

추가로 주문 상태를 표현하기 위한 enum이 필요하다.

- OrderStatus

현재 DB 설계는 다음과 같다.

members 테이블

- id: BIGINT, PK, AUTO_INCREMENT
- name: VARCHAR(100), NOT NULL
- email: VARCHAR(255), NOT NULL, UNIQUE
- created_at: DATETIME, NOT NULL

products 테이블

- id: BIGINT, PK, AUTO_INCREMENT
- name: VARCHAR(100), NOT NULL
- price: BIGINT, NOT NULL
- created_at: DATETIME, NOT NULL

orders 테이블

- id: BIGINT, PK, AUTO_INCREMENT
- member_id: BIGINT, FK, NOT NULL
- order_status: VARCHAR(20), NOT NULL
- created_at: DATETIME, NOT NULL

order_items 테이블

- id: BIGINT, PK, AUTO_INCREMENT
- order_id: BIGINT, FK, NOT NULL
- product_id: BIGINT, FK, NOT NULL
- order_price: BIGINT, NOT NULL
- quantity: INT, NOT NULL

테이블 관계는 다음과 같다.

1. members 1:N orders
   - 회원 한 명은 여러 주문을 가질 수 있다.
   - 주문 하나는 한 명의 회원에게 속한다.

2. orders 1:N order_items
   - 주문 하나는 여러 주문상품을 가질 수 있다.
   - 주문상품 하나는 하나의 주문에 속한다.

3. products 1:N order_items
   - 상품 하나는 여러 주문상품에 포함될 수 있다.
   - 주문상품 하나는 하나의 상품을 가리킨다.

4. orders와 products는 개념적으로 N:M 관계이다.
   - 하나의 주문에는 여러 상품이 들어갈 수 있다.
   - 하나의 상품은 여러 주문에 포함될 수 있다.
   - 관계형 DB에서는 N:M 관계를 직접 표현하지 않고 중간 테이블로 푼다.
   - 이 프로젝트에서는 order_items 테이블로 N:M 관계를 해소한다.

OrderItem을 만든 이유는 다음과 같다.

OrderItem은 주문과 상품의 N:M 관계를 풀기 위한 중간 엔티티이며, 주문에 포함된 상품 한 줄을 표현한다.

Product는 현재 판매 중인 상품 정보를 의미한다.
OrderItem은 주문 당시의 상품 정보를 의미한다.

예를 들어 Product.price는 현재 상품 가격이고, OrderItem.orderPrice는 주문 당시 가격이다.
상품 가격은 나중에 변경될 수 있으므로, 과거 주문 내역의 금액을 유지하려면 OrderItem에 주문 당시 가격을 따로 저장해야 한다.

따라서 order_items에는 product_id뿐 아니라 order_price와 quantity가 필요하다.

현재 JPA Entity 관계는 다음과 같이 잡으려고 한다.

- Order -> Member : @ManyToOne
- Order -> OrderItem : @OneToMany
- OrderItem -> Order : @ManyToOne
- OrderItem -> Product : @ManyToOne

처음에는 아래 관계는 만들지 않는다.

- Member -> Order
- Product -> OrderItem

이유는 다음과 같다.

Member -> Order 관계가 없어도 회원의 주문 내역은 OrderRepository에서 memberId로 조회할 수 있다.

예를 들어 DB에서는 orders.member_id가 members.id를 참조하므로, 특정 회원의 주문은 다음과 같이 조회할 수 있다.

SELECT *
FROM orders
WHERE member_id = ?

JPA에서도 Member 안에 List<Order> orders를 만들지 않고, OrderRepository에서 findByMemberId 같은 방식으로 조회할 수 있다.

Product -> OrderItem 관계도 지금은 만들지 않는다.
현재 프로젝트에서는 주문상품이 어떤 상품인지 확인하는 것은 필요하지만, 상품이 어떤 주문상품들에 포함되었는지 Product 객체에서 직접 탐색할 필요는 크지 않기 때문이다.

즉, 현재 필요한 탐색 방향은 다음과 같다.

Order
 -> OrderItem
    -> Product

주문 상세 조회 시 주문에서 주문상품 목록을 보고, 각 주문상품이 어떤 상품인지 확인하면 된다.

반대로 Product에서 자신이 포함된 모든 OrderItem을 직접 탐색하는 기능은 현재 요구사항에 없다.
나중에 상품별 판매 통계, 상품별 주문 이력 조회 같은 기능이 필요하면 Product -> OrderItem 관계를 추가할 수 있다.

현재 헷갈렸던 부분은 @JoinColumn이다.

예를 들어 Order Entity에서 다음과 같이 작성한다.

@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "member_id")
private Member member;

여기서 name = "member_id"는 Member 테이블 안에 있는 member_id 컬럼을 의미하는 것이 아니다.
현재 Entity인 Order가 매핑되는 orders 테이블에 생길 FK 컬럼명을 의미한다.

즉 DB 관점에서는 다음과 같다.

orders.member_id -> members.id

자바 객체 관점에서는 다음과 같다.

Order.member -> Member 객체 참조

@JoinColumn(name = "member_id")는 orders 테이블에 member_id라는 외래키 컬럼을 만들고, 그 컬럼으로 members 테이블의 id를 참조하겠다는 뜻이다.

참조 대상 컬럼을 명시하려면 다음처럼 쓸 수 있다.

@JoinColumn(name = "member_id", referencedColumnName = "id")

하지만 referencedColumnName = "id"는 기본값이라 보통 생략한다.

현재 application.properties는 MySQL 연결을 위해 다음과 같은 형태로 설정하려고 한다.

spring.application.name=shopping-mall

spring.datasource.url=jdbc:mysql://localhost:3306/shopping_mall?serverTimezone=Asia/Seoul&characterEncoding=UTF-8
spring.datasource.username=shopping_user
spring.datasource.password=실제비밀번호
spring.datasource.driver-class-name=com.mysql.cj.jdbc.Driver

spring.jpa.hibernate.ddl-auto=create
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true

ddl-auto=create는 Entity 기준으로 테이블을 매번 다시 생성하기 위한 학습용 설정이다.
초기 Entity 설계 단계에서는 create를 사용하고, 나중에 데이터 유지가 필요하면 update로 바꿀 수 있다.

show-sql=true는 Hibernate가 실행하는 SQL을 콘솔에 보여주기 위한 설정이다.
format_sql=true는 출력되는 SQL을 보기 좋게 줄바꿈해서 보여주기 위한 설정이다.

MySQL Workbench에서는 기존 DB와 섞이지 않게 하기 위해 프로젝트 전용 DB와 계정을 만들었다.

DB 이름은 shopping_mall이다.
계정 이름은 shopping_user이다.
shopping_user는 shopping_mall DB에만 권한을 가지도록 설정했다.

주의할 점은 Order Entity에서 member_id를 Long으로 두면 안 된다는 것이다.

잘못된 예:

@ManyToOne(fetch = FetchType.LAZY)
private Long member_id;

@ManyToOne은 Long 같은 기본 값 타입에 붙이는 것이 아니라 Entity 객체에 붙여야 한다.

올바른 예:

@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "member_id")
private Member member;

즉, JPA에서는 FK 값을 직접 Long으로 들고 있는 것이 아니라, 객체 참조로 관계를 표현한다.
DB에는 member_id가 저장되지만, Java 코드에서는 Member 객체로 연결한다.

id 자동 생성은 MySQL AUTO_INCREMENT에 맞춰 다음을 사용한다.

@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;

@GeneratedValue(strategy = GenerationType.IDENTITY)는 기본키 생성을 DB의 AUTO_INCREMENT에 맡긴다는 뜻이다.
현재 MySQL을 사용하고 있고 DB 설계에서도 id를 AUTO_INCREMENT로 잡았으므로 IDENTITY를 명시하는 방향으로 간다.

만약 @GeneratedValue만 쓰면 기본값은 GenerationType.AUTO이고, Hibernate가 DB에 맞는 전략을 자동 선택한다.
하지만 지금은 MySQL AUTO_INCREMENT를 명확히 쓰고 싶으므로 IDENTITY를 사용한다.

자바 필드명은 DB처럼 created_at이 아니라 createdAt으로 작성한다.
DB 컬럼명은 필요하면 @Column(name = "created_at")으로 맞춘다.
Spring Boot/Hibernate 설정에 따라 createdAt이 created_at으로 자동 매핑될 수도 있지만, 학습 목적상 명시해도 된다.

현재 원하는 작업은 다음과 같다.

1. 위 설계에 맞춰 Entity 코드를 작성한다.
2. 처음부터 너무 복잡한 기능을 추가하지 않는다.
3. Lombok은 @Getter 정도만 사용하고, @Setter는 가능하면 사용하지 않는다.
4. 기본 생성자는 JPA 때문에 필요하므로 protected 기본 생성자를 둔다.
5. 테이블명은 @Table로 명시한다.
6. FK 컬럼명은 @JoinColumn으로 명시한다.
7. OrderStatus는 @Enumerated(EnumType.STRING)으로 저장한다.
8. Order와 OrderItem의 양방향 관계에서는 mappedBy를 정확히 사용한다.
9. 무한 참조나 JSON 응답 문제는 나중에 Controller/DTO 단계에서 처리한다.
10. 지금은 Entity 생성과 테이블 생성 확인까지만 목표로 한다.

원하는 Entity 코드 스타일은 다음과 같다.

- 과한 설계를 하지 않는다.
- Builder, 정적 생성 메서드, 도메인 메서드는 처음부터 너무 많이 넣지 않는다.
- 먼저 JPA 연관관계와 테이블 생성을 확인하는 데 집중한다.
- 이후 주문 생성 기능을 구현할 때 생성 메서드나 편의 메서드를 추가한다.

우선 지금 필요한 것은 Member, Product, Order, OrderItem, OrderStatus의 가장 기본적인 JPA Entity 코드다.
